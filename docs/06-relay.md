# 出门之后：三条路的降级链

手机跟电脑说话，有且只有三种可能的路。它们不是三个选项，是**一条按代价排好的阶梯**：
每一条在它上面那条不通时才被尝试。

| 档 | 名字 | 走什么 | 什么时候用 | 代价 |
| --- | --- | --- | --- | --- |
| 一 | `lan` | 同一个 Wi-Fi 直连 `http://<电脑IP>:<lanPort>` | 人在家、手机和电脑同一个网 | **出了门就不存在** |
| 二 | `relay.self` | 宿主出站连 NAS 上的中转（`relay/`），手机从中转进来 | 不在同一个网 | 整条链路压在 NAS 的机器与它的公网上行上；家里断网、NAS 关机就没了 |
| 三 | `relay.fallback` | 同一个 `relay/` 镜像，部署在**另一个故障域**（云主机、或 Cloudflare Tunnel 后面的另一台） | 自建中转不可达 | 多一跳、受第三方限流；数据经过别人的基础设施 |

实现：`backend/src/app/relay-chain.ts`。配置：宿主上 `CREW_RELAY_URLS`，逗号分隔，第一条是自建，其余是兜底。

## 为什么是这三条，而不是「两条一样的隧道」

先说结论：**兜底与被兜底不能共享故障域**。如果把兜底也做成「同一个 NAS 上的第二个端口」，
它覆盖的是「进程挂了」，不是「NAS 或家里的网挂了」—— 后者才是出门在外最常遇到的。

三条路的性质分别是「物理上最近」「自己的基础设施」「别人的基础设施」，失败原因互相独立：
Wi-Fi 断了但公网还在、公网断了但局域网还在、NAS 挂了但 Cloudflare 还在。

## 为什么不是「再发明一个长轮询通道」

提这个方案时最容易想到的是：自建中转挂了就退回 HTTP 长轮询。问题在于那会引入**第二套语义** ——
消息顺序、取消、流式、背压，每一件都要在长轮询里重新定义一遍，而两套语义一旦不同步，
bug 会出现在最难复现的那个组合里（某一条路某一种时序）。

兜底要解决的问题是「**那个落地点在哪**」，不是「再发明一套线格式」。所以兜底复用同一个协议、
同一个镜像，只是换一个落地点。这也让运维只学一套：`docker compose up -d` 与 `curl /health`
在两条路上是一样的。

## 顺序为什么是这样

- `lan` 排第一：零公网依赖、少两跳、不受中转的带宽与限流影响。同一个 Wi-Fi 下没有理由绕道。
- `relay.self` 排第二：自己的机器、自己的带宽，可控。
- `relay.fallback` 排最后：多一跳、有第三方的限额与可用性，且数据经过别人。

顺序写在 `relay-chain.ts` 的文件头，改它要改那里 —— 让「为什么先试这条」有唯一答案。

## 探测与记忆

- 每一档的「通不通」是**真的探一次**，不是猜。局域网那档发一个真实 HTTP 请求；
  判据是「有响应」，不是「200」—— 消息面在没配对时本来就回 401，而那恰恰说明路是通的。
- 探测有自己的超时（默认 2s）。公网上最常见的故障不是「连接被拒」而是「连上了但不回」；
  一个卡死的探测不设上限，会把整条阶梯永远停在第一档。
- 选中的那档会被**记住**，直到它不通。否则每个请求都要先从最便宜的探起，等于给每个请求
  加一次「局域网不通」的超时。
- 当前那档坏了之后，从**阶梯顶端**重新试：兜底挂了的时候，宿主可能已经回到局域网里了。
  直接跳到第三档会白白多绕两跳。
- 探测函数自己抛错（DNS 炸了、证书错）与返回 false 同义：这条路现在不通，试下一条。

## 一条都不通时

`choose()` 返回 `undefined`，不抛错。没有路是**此刻的处境**，不是程序错误 ——
手机上表现为「连不上」，而宿主该做的是继续按退避重试，不是崩掉。

## 切换是怎么发生的

`CREW_RELAY_URLS` 里的地址按顺序交给 `createTunnel` 的 `relayUrl`（一个数组）。
隧道的重连本来就是「失败 → 退避 → 再连」，切换只是在这个循环里多走一步：

```
连 wss://jarvis.kentonnie.top/crew-relay/tunnel ── 失败 ──► 换 wss://relay-b.example
                                            │
                                    连上了（registered）
                                            │
                                    钉在这里，直到它也断了
                                            │
             ── 失败 ──► 回到 wss://jarvis.kentonnie.top/crew-relay/tunnel
```

- **轮转是固定顺序**，不是在运行时重新排序。第 1 条只是暂时不通，它优先是有原因的。
- **`attempt` 不因换地址而清零**：刚换了一条地址不等于「该从头快速重试」，
  新地址大概率也是同一个原因不通（家里断网 → 两条都连不上）。
- 全部轮完回到第 1 条，所以第 1 条恢复之后会自动被重新用上。

  但宿主启动时把 `CREW_RELAY_URLS` 原样交给隧道、没有先探一遍再选；接上它需要把
  `choose()` 放进 `start()` 之前，并让 `invalidate` 接在隧道的断开回调上」。
- **这一半已落地**：`backend/src/index.ts:140` 先 `await orderRelays(relays)`，
  `:189`–`:203` 用 `createChain(...).choose()`（`relay-chain.ts:85`，带 2s 超时的
  WebSocket 握手 `index.ts:206`）逐条探一遍，选中的提到数组首位，`:144` 交给
  `createTunnel`、`:177` 才 `void tunnel.start()` —— `choose()` 确实在 `start()` 之前；
  全不通退回原顺序。`backend/tests/index.spec.ts` 3 例覆盖排序。
- **剩余真实缺口**：
  - `invalidate` 仍未接断开回调：`relay-chain.ts:55` / `:99` 只有接口声明与实现，
    生产代码零调用点（唯一调用在单测 `tests/relay-chain.spec.ts:107`）；`tunnel.ts`
    的 `TunnelOptions` 也没有断开回调，`close`（`tunnel.ts:264`）只清在途请求并推进
    `cursor` 轮转，「某档坏了就从阶梯顶端重探」在运行态没有发生。
  - `orderRelays` 里的 `createChain` 是选完即弃的局部对象（`index.ts:196`），链的
    「记住选中档」没有跨请求复用：进程只在启动时选一次，之后全靠隧道自己的 `cursor` 轮转。
  - `lan` 档不参与这一步：出站隧道只用 `relay` / `fallback` 两档（`index.ts:138`）。
- ~~**局域网与中转之间没有自动切换**~~：手机侧 `CrewClient.read()` 已按
  `CrewRoute.entries()`（P2P → 局域网 → 公网）逐条试，`IOException` 就绕到下一条、成功即记住
  当前入口（401 不换，那是凭据问题）；`CrewClientRouteTest` / `CrewRouteTest` 有单测。这句是 11-10
  写的，11-12 `065fe82` 之后已过期，别照着它去重做。
- **跨网域的主答案是 P2P，不是重新发现**：`tailcat serve --key=default` 用固定密钥，tc-addr 重启
  不变；手机侧 `TailcatP2p` 在 `127.0.0.1` 起本地代理、`promote()` 提到队首。换 Wi-Fi、开热点、
  出门用蜂窝都不受影响，配对时存下的 `p2pAddr` 是网域无关的公钥身份，不是「记住旧网关」。
  会随网段失效的只有 `base`（LAN IP），而它只在 P2P 没起来时当第二条路。
- **P2P 没起来时的 LAN 兜底**：配对时把 mDNS TXT 的 `crew` 指纹连同 `pub` / `p2p` 一起落盘；
  同网段重新发现时按指纹认出同一台，用 `CrewClient.replaceEntries()` **就地**换入口表——
  特意不改 `paired` 状态，否则会重启 `LaunchedEffect`、重建 tailcat 句柄，把正在跑的隧道打断。
  发现流去重改成按「地址 + 路由 + 指纹」签名：原来只按服务名去重会吞掉同一台换 IP 后的重新广播。
  `CrewRefreshTest` 9 例 / `CrewClientRouteTest` 换表 4 例 + 三处反向验证。**真机未验**（无 adb 设备）：
  P2P 换网不断线、LAN 兜底刷新、权限被拒的降级路径都还需一次实机走通。
- 中转不支持 WebSocket 隧道（`wsUpgrade` 一族）：消息面全是请求-响应，用不到。
