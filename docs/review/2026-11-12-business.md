## 2. 契约 vs 实现偏差：文档自我降级

方法：对 `docs/00-contract.md` 全文扫「这一轮不 / 还没有 / 暂时 / 没接 / 不做 / 尚未 / 留到」，逐条回到代码。共 18 处命中，其中 **3 处属文档自我降级**（实现已经追上，文档还在说没有），1 处属**能力已扩张但文档没写**，其余 14 处文档准确。

### 2.1 【自我降级·确认】`contract.md:351` 说没有往 worker 敲字的通道

> 原文：「手机上能往 worker 递话的只有 §5.3 的 steer（一句消息，在下一步边界读到），**没有直接敲终端的通道**。」

**实际**：`POST /api/mobile/steer` 已通，且是两条真路径 —— 有 `text` 时走网关 `POST /gateway/send`，带 `steer: true` 插队；无 `text` 时走 `POST /gateway/claim` 认领队列里已有的消息，`404/409` 有明确拒绝分支。
证据：`backend/src/app/mobile-http.ts:583-614`（`已验证`），注册在 `:983`。

**判定**：文档把「一句话 steer」描述成唯一通道，实际上 steer 本身已经是完整的递话通道（含插队与认领两种语义）。**建议改写**：不说「没有通道」，说「通道是消息级不是会话级 —— 一句消息在下一步边界被读到，不能交互式敲终端」。这是**能力描述精度**问题，不是缺失。

### 2.2 【自我降级·确认】进度三端口径，文档说「缺省 0」，实现是三端都画

> 原文（`contract.md:170-177`）：「`total_steps` 随之变小（进度条可能因此回退），这是真话，不做单调化…… 三端都按本节画：`desktop/ui.go` 的 `progressOf`、`CrewWire.kt` 的 `progressOf`（`WorkTicket` 上的 `totalSteps` / `stepsDone` **缺省 0**）、`CrewUi.kt` 的 `TaskRow` 仅当 `totalSteps > 0` 时画一条 3dp 的轨道」

**实际**：手机端两点都落地了。字段在 `app/app/src/main/java/com/dsh/botcrew/CrewWire.kt:338` `val totalSteps: Int = 0`、`:343` `val stepsDone: Int = 0`；绘制在 `CrewUi.kt:2128-2140`（3dp 高轨道 + `fillMaxWidth(done.toFloat() / total.toFloat())` 按比例填充，`done > 0` 才画填充）。
`已验证`。

**判定**：**这条其实文档是对的**（它说三端都画），但「缺省 0」这句读起来像「手机端还没接」。真正的风险是**读者误读**，不是文档撒谎。**建议**：把「缺省 0」改成「后端未下发计划时为 0，此时不画轨道」——同一个事实，去掉可被读成「未实现」的余地。

### 2.3 【自我降级·半条】`contract.md:353` 说「像素级画面、全屏：都还没有」

> 原文：「**像素级画面、全屏：都还没有。** 按下去要如实说没接上，不做成看起来能用的形状。往终端敲字走 §5.3 的 steer（一句话，不是一段会话）。」

**实际**：`GET /api/mobile/screen` 存在且返回真实内容 —— 但**不是像素截帧**，是「会话活动快照（命令 / 输出 / 回话）」。
证据：`mobile-http.ts:965`（注册）、`:633-639`（实现，注释原文即「画面源是会话活动快照……不是像素截帧」）。`已验证`。

**判定**：**一半是自我降级，一半是准确**。
- 「全屏 / 像素级截帧」：**确实没有**，文档准确。
- 「都还没有」：**不准确** —— 有一个降级形态的画面源已经上线，且降级文案（`reason: '后端还没有接入画面源'`、`'这张工单的会话暂时读不出来'`）都写好了。手机用户现在**能看到 worker 在终端里干了什么**，只是看不到屏幕。
- **建议改写**：「画面源是会话活动快照，不是像素截帧。全屏截帧没有。」—— 一句话，把「没有」收窄到真正没有的那一项。

### 2.4 【文档滞后·能力扩张】`contract.md:558` 说常规任务「这一轮没有写接口」

> 原文：「只有这一条路由，**这一轮没有写接口**：改账（加 / 改 / 开关 / 删）还没有决定由谁来写，不先开一个只能看不能改的假入口。」

**实际**：`/api/mobile/routines` 在 `mobile-http.ts:969` **只有 GET**，没有 POST。`已验证`。
**但**：`/api/mobile/bots` 在 `:986` 是 **GET + POST**，且 POST 走 `action=edit / remove`，带完整的 `default` 顶替逻辑与 `bot_id` 不可变约束（`:665-700`，`已验证`）。

**判定**：契约这句话对 routines 是**准确的**，但整份文档读下来会让人以为「手机端只能读不能写」。事实上**队伍配置已经是可写的**（加人 / 改人设 / 撤人），而且写入语义设计得比 routines 更成熟（`bot_id` 不可改因为记忆命名空间挂在上面）。**建议**：§5「队伍」一节补一句「手机端可写队伍配置；routines 是唯一明确只读的账本」，把「哪些能写」摊开说，别让读者自己在 23 条路由里猜。

### 2.5 其余 14 处：文档准确，不重复列举

- `:135`（`queued` 定义）、`:280`（可撤回的双条件）、`:334/:337`（工单无记录的两种空态）、`:455-456`（产出物 `empty` vs `unavailable`）、`:501/:547-549`（常规任务空态与「不得说还没有」）、`:616`（未读回话这条数**确实没有**，`unreadOf` 在 `mobile-http.ts:920` 只数发出去没被读走的 —— 与文档一致，`已验证`）、`:661/:667`（记忆 `superseded` 纠错写新条）、`:697`（配对唯一例外）。
- 这批的共同点：**空态与降级态的措辞是这套契约最强的地方**。「读不到」与「确实没有」被反复要求分开说，且代码里每一处 `state: 'unavailable'` 都配了中文 `reason`。这是产品级的设计，不是工程副产品。

## 3. 产品定位判断

**结论：这是一台「多 agent 任务的远程遥控器」，不是「团队共享工作台」。而且它自己也知道，只是在文案上还没承认到底。**

按能力分布判断，不看文档野心：

**支持「遥控器」的证据（压倒性）**
- 25 个方法里，**19 个是「看状态」或「对一张票下指令」**：timeline / work / agents / models / efforts / outputs / routines / spend / audit / reply-spend（10 个只读）+ send / withdraw / model / takeover / retry / steer / pause / voice / speak（9 个动作，全部以 `ticket` 或 `request_id` 为寻址单位）。
- 核心对象是**工单（ticket）**：`steer` 要 `ticket` + `request_id`（`mobile-http.ts:588-590`），`takeover` 要 `ticket`（`:645`），`pause` 的 `scope` 只有一个值 `executor`（`:661`）。**所有动作的粒度都是「这一张票」或「整台执行器」，没有一处是「这个项目」或「这个团队」。**
- `pause` 的 `scope: 'executor'` 是**最诚实的定位声明**：手机能停的只有执行器，而且停了要去桌面恢复。遥控器上不会有「恢复」按钮 —— 因为它不是工作台。

**反对「共享工作台」的证据**
- 没有多用户概念。配对是**设备**凭据（`phone-gate.ts:44` 唯一免凭据例外是首次配对），`devices` 是设备表不是成员表。
- 没有协作原语：没有分配、没有 @、没有评论、没有并发编辑冲突处理。`bots` 的 `action=edit` 是**单写入者覆盖**（`:695-700` 直接 `map` 出 `next` 再整体 `saveTeamBots`），两个人同时改就是后写覆盖先写。
- 「队伍」这个词指的是 **Bot 花名册**（`persona` / `role` / `default_bot_id`），不是人类同事。

**产品含义（这才是要点）**
1. **遥控器的第一性需求是「我离开时它别停」**。现在最弱的一环恰恰是这里：`pause` 只能全局停、`takeover` 只能停票、**没有任何「放它继续跑」的入口**（恢复在桌面）。手机上按暂停之后，人还在外面，票就是死的。
2. **遥控器的第二性需求是「一眼知道我该不该管」**。`routines` 只读、未读回话这条数没有（`contract.md:616`）—— **两个「该我出手了」的信号，一个不能改、一个不存在**。徽标只能数「发出去没被读走的」，数不到「队伍在等我」。
3. **共享工作台是错的野心**。真要往工作台走，缺的不是功能是**身份模型**（设备 → 成员），那是重写 `phone-gate.ts` 和整个审计面的事。当前 23 条路由里没有一条为多用户留了位置，现在不该往那个方向投人。

## 4. 最该做的三件事（按投入产出比排）

### 第一件：手机端「恢复执行」入口 —— 半天，补上一个让产品成立的动作

**问题**：`pause` 在 `mobile-http.ts:653-663` 已经实现且 `scope: 'executor'` 说得清清楚楚，但**恢复只能在桌面面板**（`contract.md:351` 原文：「恢复要去桌面面板」）。手机按了暂停，人在外面，唯一的出路是回工位 —— 这直接否定了「远程遥控」的产品前提。

**做法**：开 `POST /api/mobile/resume`，语义与 `pause` 对称（无 body，`settings.pause(false, 'panel')`），手机端在暂停成功后原地把按钮切成「继续」。**不要**做成新契约 —— `scope` 字段已经预留了口子，只是这一半没接。

**为什么排第一**：它是**唯一一个「不做就等于产品不成立」的洞**，而成本是 10 行路由 + 一个按钮态。投入产出比压倒性。

### 第二件：把 `contract.md` 的三处自我降级改掉 —— 两小时，零代码

**问题**：`§2.1`（steer 通道说成「没有」）、`§2.3`（画面源说成「都没有」）、`§2.4`（没说队伍可写）**让后来者按错误的现状做决策**。最贵的不是写错代码，是有人读完契约判定「这块没做」然后重做一遍 —— 而 `steer` 的插队/认领两条语义（`:596-614`）重做一次未必能对。

**做法**：三处各改一句，都在本报告 §2 给了改写文本。**顺带**把 `§1.2` 表里「`未验证`」的桌面端四入口补成实测（`desktop/ui.go` 的 `progressOf` 起手）。

**为什么排第二**：零代码、两小时、直接防止一次重复劳动。唯一的成本是承认「文档落后于代码」—— 而这套契约的可信度恰恰建立在「说了就是真的」上，**自我降级比吹牛更伤**。

### 第三件：未读回话（`contract.md:616`）—— 一个后端字段，解锁整个「该我管」的入口

**问题**：文档说得很硬：「没有记录，所以没有这条数……这一轮不编」。**这个判断我不反对**（凭空造数是错的），但结论下早了。缺的输入只有一样：**客户端把自己的已读位置报上来**。手机端本来就有时间线（`:954`），读到哪一条是本地已知的。

**做法**：`POST /api/mobile/read`（`{ ticket, last_read_at }` 或 `{ ticket, last_read_id }`），后端在 `replies` 侧记一个水位，徽标多一个数。**闭环条件**：契约里那句「两个数会不一样，两个都要各自的定义，谁也不冒充谁」（`:618-619`）已经写好了 —— 加完这条数，那句话才从「为什么没有」变成「怎么区分」，产品语言自动对上。

**为什么排第三**：它比前两件重（要动 `replies` 表 + 一个新路由 + 两端），但它是**唯一一个能把「遥控器」从「看状态」升级成「知道什么时候该出手」的动作**。前两件做完，产品是「能用」；这件做完，产品是「值得装」。

**明确不建议做的**：往「团队共享工作台」走（`§3`）。缺的是身份模型，不是功能，当前 23 条路由没有一条为它留位置。
