**最要紧的三件事**

1. **契约 §5 两处「手机端还没接」已经过期**（`docs/00-contract.md:173-178`、`:257-260`）。实现不但接了，还带了夹取、只画轨道、失败分离等文档没写的规则。文档不更新，下一个人会按「还没做」去重做一遍。

## A. 文档与实现偏差（最高价值，建议单独立项清理）

这一组不是「UI 丑」，是**文档与代码对同一件事给出相反事实**。按经验，这类偏差拖久了会让人重做已完成的工作，或者相信一份不存在的约束。

### A1 · 契约说手机端没解析 `total_steps` / `steps_done`、`TaskRow` 没进度条 — 实际全都有

**文档**（`docs/00-contract.md:173-178`）：

> 手机端这轮**只读不改**：`app/.../CrewWire.kt` 的 `WorkTicket` 还没有 `total_steps` /
> `steps_done` 两个字段，`CrewUi.kt` 的 `TaskRow` 也没有进度条。要接的时候按本节做……

**实现**：

- 字段与解析：`app/app/src/main/java/com/dsh/botcrew/CrewWire.kt:338`（`val totalSteps: Int = 0`）、`:340`（`stepsDone` 注释）、`:242`（`totalSteps = task.optInt("total_steps", 0)`）
- 夹取规则：`CrewWire.kt:357-360` —— `totalSteps <= 0` 直接返回 `0 to 0`；`stepsDone.coerceIn(0, totalSteps)`，理由注释写明「后端版本可能不一致」
- 绘制：`CrewUi.kt:2128-2147` —— 仅当 `total > 0` 才画 3dp 轨道，`done > 0` 才画填充，注释说明「零步走完时只画轨道：宽度 0 的填充在某些引擎上仍会留下一个点」
- 测试覆盖：`app/app/src/test/java/com/dsh/botcrew/CrewWireTest.kt:1060-1152`，共 10 个用例，含越界（`:1082` `steps_done:5 > total:3`）、负数（`:1086`）、只有分母（`:1099`）、只有分子（`:1104`）、零步（`:1115`）、负数计划（`:1120`）、走完（`:1130`）、改计划回退（`:1149-1152`）

**判断**：实现比文档描述的**更严格**（文档只要求「自行夹一次」，实现还处理了「只有分子不画」这种反例）。文档该整段改写成「已实现 + 现有口径」，并把 `:1130` 那条「走完」用例的语义（`completed` + `3/3`）写进去。

### A2 · 契约说手机端没接「采用」/「看看改完的样子」两个按钮 — 实际已接且带完整状态机

**文档**（`docs/00-contract.md:257-260`）：

> 手机端这轮还没接这两个按钮，只有代码卡（`app/.../CrewUi.kt` 的 `CodeCard`）：
> 它读 `Message.code`，`ticket_ref` 与代码块里的 `id` / `ticket_ref` 还没解析，
> 所以「看看改完的样子」在手机上暂时无处可去。

**实现**：

- `ticket_ref` 已解析，且**代码块优先于消息**：`CrewWire.kt:124` —— `block.optString("ticket_ref").trim().ifEmpty { ticketRefOf(item) }`；`:110` 注释明确写了「票号优先取代码块自己的，其次才取消息上的 `ticket_ref`（契约 §5：两处都可，代码块里的优先）」
- 两个字段都在：`CrewWire.kt:27`（`Message.ticketRef`）、`:46`（代码块 `ticketRef`）
- 按钮文案已定义：`CrewWire.kt:703` —— `const val PREVIEW = "看看改完的样子"`
- 采用状态机：`CrewUi.kt:2344-2345`（`adopting` / `adopted` 两个 `remember`）、`:2434`（`clickable(enabled = !adopting && !adopted)`，防重复点）、`:2448`（成功置 `adopted`）、`:2451`（失败走 `CodeCopy.adoptFailed`）、`:2463-2464`（进行中/已采用文案）
- 按钮可见性有独立规则函数：`CrewUi.kt:2352` —— `val buttons = CodeCardRules.showsButtons(block)`，对应契约「代码块缺失或为空时不画按钮」
- 失败话术分离：`CrewWire.kt:700` —— 「采用失败。和『看看改完的样子』失败分开说，不混成一句」
- 屏幕预览：`CrewUi.kt:1154-1164`（`barTicket` —— 只认消息自己带的 `ticket_ref`，「绝不拿别的票顶替」）、`:602`、`:746`、`:1063`

**判断**：这不是「没做」，是**超额完成**。文档 `:257-260` 整段应删掉，改为描述现状：`ticket_ref` 双来源优先级、`showsButtons` 的空块规则、`adopting/adopted` 的本地态不落盘。

### A3 · 观察：这类偏差是系统性的，不是孤例

两处都是「手机端还没接 X」，两处 X 都已经接了。建议在 `docs/00-contract.md` 里加一条**维护约定**：凡写「客户端还没接」的句子，必须同时写上「截至哪个 commit / 日期」，否则过期无人发现。或者更省事：把 §5 里所有「还没接」改成 `TODO(owner, 日期)` 形式，让 grep 能捞出来。

## B. 可访问性

### B1 · P1 · 亮色 Hint 当正文用，对比度 2.41:1

**证据**：

- 色值：`desktop/theme.go:96` —— `Hint: ui.Hex("#A9A294")`，注释写「比 Faint 再淡一档：占位、极弱说明」
- 底色：`LightPalette.Surface` = `#FBF9F6`
- 实算：**2.41:1**（WCAG 相对亮度公式，`contrast_test.go:15-34` 同一套算法）

**它压在哪**（都取 `desktop/ui.go`）：

| 行 | 文案 | 字号 |
|---|---|---|
| `:1501` | 「在下面写一句，他就会记得。」 | `FontLabel` |
| `:2730` | 「队伍接到的活会出现在这里。」 | `FontBody` |
| `:1829` | 「自己写一句…」（输入框占位） | `FontBody` |
| `:3607`、`:3650` | 提示行 | `FontTiny` / `FontHairline` |

这几句里，`:1501` 和 `:2730` 是**空态说明**——用户第一次打开时唯一的指路信息。占位符可以淡，但「他接活后右栏能看到进度」这种句子不能只有 2.41:1。

**为什么测试没拦住**：`desktop/contrast_test.go` 的 `TestTextIsReadableOnItsBackground`（`:36-65`）测了 Ink / Muted / UserInk / Accent 各自压在 Surface 或 Card 上，**唯独没有 Hint**。`TestFaintTextStillVisible`（`:68-77`）只测 `Faint on Card`（2.5 的门槛，很松），而 Faint 实际大量压在 Surface 上（`ui.go:1492`、`:1772`、`:1796`、`:1816`）。

**实算的完整未覆盖表**（本次计算，可直接抄进测试）：

```
2.41  亮 Hint  on Surface  ← 空态正文，不达标
2.54  亮 Hint  on Card
3.27  暗 Hint  on Surface  ← 空态正文，不达标
2.86  暗 Hint  on Card
3.57  亮 Faint on Surface
2.02  亮 EmptyGlyph on Surface   ← 「+」/「···」空态字形
1.68  亮 EmptyGlyphSoft on Surface
2.23  亮 Hint  on Field（占位符压在输入框底上）
2.64  暗 Hint  on Field
5.74  亮 Accent 文字 on Surface  ← 这条过了，页头按钮没问题
4.92  亮 Danger on Card          ← 刚过 AA，无余量
```

**建议**：

1. 亮色 Hint 从 `#A9A294` 压到 **`#6F6A60` 附近**（对 Surface 约 4.6:1）。视觉上仍是「淡」，但读得清。
2. 或者按用途拆两档：`Hint`（占位符，可 3:1）+ `HintText`（空态说明，必须 4.5:1）。现在的 `Hint` 一个值干两件事。
3. 把上表整个补进 `contrast_test.go`，按「前景 × 实际背景」逐对列，而不是每个前景只测一个背景。

### B2 · P2 · 暗色 EmptyGlyph 与亮色差 2.7 倍

`desktop/theme.go:109` 亮色 `EmptyGlyph: #B8B1A5`（2.02:1），`:140` 暗色 `EmptyGlyph: #928C82`（5.40:1）。同一个空态图标，两套主题的可读性差 2.7 倍。亮色那档基本是「看得见但看不清」。若视为纯装饰（有 `+` 语义），2.0 尚可接受；但它是空态里唯一的图形提示，建议提到 3:1 以上。

### B3 · P2 · 手机花名册：32dp 触控目标 + 无横向滚动

**证据**（`app/app/src/main/java/com/dsh/botcrew/CrewUi.kt`）：

```kotlin
// :663-666
Row(
    modifier = Modifier.fillMaxWidth().padding(horizontal = 14.dp, vertical = 6.dp),
    horizontalArrangement = Arrangement.spacedBy(16.dp),   // ← 只有间距，没有 scroll
) {
    for ((index, bot) in shown.bots.withIndex()) {
        Column(
            horizontalAlignment = Alignment.CenterHorizontally,
            modifier = Modifier.clickable { profile = bot },  // ← 点击区 = 整列
        ) {
            Box(modifier = Modifier.size(32.dp) ...)         // ← 32dp
            Spacer(Modifier.height(3.dp))
            Text(bot.name, fontSize = 11.sp, ...)
```

**两个问题**：

1. **溢出**：`Row` 没有 `horizontalScroll`（全文件计数 0）。每个 Bot 宽 `max(32, 名字文字宽)` + 16dp 间距。按 4 字中文名（11sp ≈ 44dp）算，每位约 60dp，360dp 宽屏幕减 28dp 内边距后**只能放 5 位**，第 6 位开始被硬裁。名字长的（英文名、带后缀）更早溢出。裁掉的一侧没有任何视觉提示（没有 mask、没有渐变），用户会以为「就这么多人」。
2. **触控目标**：Material 建议最小 48×48dp。头像 32dp 见方，加上下方文字，整列约 32×46dp，宽度不足 48。`spacedBy(16.dp)` 的间距不属于点击区，所以相邻两位之间的可点宽度就是 32dp。手指按偏一点就是「点了没反应」。

**建议**：

- 给 `Row` 加 `Modifier.horizontalScroll(rememberScrollState())`，并在两端加 `contentPadding`，让最后一位能完整滚进来。
- 头像提到 36–40dp，或给 `Column` 加 `Modifier.padding(vertical = 4.dp)` 把高度补到 48dp。
- 溢出时用 `CrewUi.kt:178` 那种 `mask-image` 等价的 Compose 方案（`drawWithContent` + 渐变）给边缘一个「还能滚」的提示。

> 顺带：`client.css:178-180` 的 Web 面板已经处理了同类问题——`.dt-tabs[data-more='both']` 用 `mask-image` 做两端渐变。手机端可以照抄这个思路。

### B4 · P2 · 手机字号：11sp 用了 64 处，10.5sp 用在结果回执

**证据**（`CrewUi.kt` 统计）：

```
10.sp    2 处
10.5.sp 10 处
11.sp   64 处   ← 主体
11.5.sp  8 处
12.sp   13 处
13.sp   22 处
```

Material 3 的 Body Small 是 12sp，Label Small 是 11sp。11sp 大量用在**状态行、任务详情、时间戳**这类真正的信息文本（如 `CrewUi.kt:2082` 的答案结果「已发送」、`:1276` 的说明），不是纯标签。10.5sp 更低。

**建议**：11sp 保留给真正的 Label（徽标、单位），信息文本统一提到 12sp。10.5sp 全部消掉——它只比 11sp 小 0.5，视觉上分不出层级，只增加阅读成本。

### B5 · P2 · 手机小按钮：32dp 高、「回」36×32dp

- `CrewUi.kt:2074` —— 「自己写一句…」的 Box `height(32.dp)`
- `CrewUi.kt:2086-2090` —— 「回」按钮 `size(width = 36.dp, height = 32.dp)`

这两个是**待决卡片（等你决定）上的主操作**——用户要在这里回答「谁接手」。32dp 高低于 48dp 最小目标，且在卡片这种「需要精确点」的位置。建议至少 40dp，最好 44–48dp。

### B6 · P2 · Web 面板 11px 标签

`backend/src/client/client.css:198` —— `.dt-tag { font-size: 11px; line-height: 17px; }`。11px 在桌面浏览器（尤其 1x 屏）已经是「能读但要凑近」的下限。`.dt-rule-preview`（`:99`）和 `.dt-mono`（`:82`）都是 12px，`.dt-tag` 比它们还小。

标签本身短（2–4 字），11px 勉强可接受，但如果标签里放的是**状态词**（「运行中」「已合并」），建议提到 12px 与其余元信息对齐。

## C. 布局与响应式

### C1 · P2 · 桌面侧栏收起条宽 30px

**证据**（`desktop/ui.go:840`）：

```go
ui.Row(c).Width(30).FillHeight().Background(p.Card).Cursor(ui.CursorPointer).
    AlignItems(ui.Center).OnClick(func() { s.sidebarClosed = false }).Children(...)
```

高度铺满（`FillHeight`），但宽度只有 30px。这是个**只能靠点击复原侧栏**的窄条——侧栏一旦收起，用户唯一的出路就是命中这 30px。鼠标尚可，触控板/触屏偏一点就落空。

**建议**：视觉上仍画 30px 的条，但把点击区用负 margin 或外层透明 Row 扩到 44px。或者把「»」做成一个 44×44 的透明热区叠在条上。

### C2 · 未验证 · Split 拖到极窄时按钮是否被压缩

`desktop/ui.go:854-874`：标题行 `ui.Row(c).FillWidth().AlignItems(ui.Center).PaddingX(8).Gap(9)`，里面是「◎」+ 标题（`MaxLines(1).Ellipsis("…")`）+ `Grow(1)` 弹簧 + 28×28 的「+」+ 带 `Padding(6)` 的「«」。

注释（`:859`）写「标题与两个按钮抢一行：栏拖窄时标题先省略，按钮不能再被挤出去」——**意图正确**，但 mygo 的 `Grow(1)` 是撑开还是「吃掉剩余空间」，以及两个定宽按钮在不同 `sidebarWidth` 下的实际表现，需要跑起来量。**未验证**：请在 `sidebarWidth` 拖到 180 / 140 / 100 时截图。

### C3 · 未验证 · Web savebar 底部留白叠加

`client.css:151` `.dt-savebar { position: sticky; bottom: 0; padding: 12px 0; }`
`client.css:7` `.dt-page > .dt-column { padding-bottom: 48px; }`
`client.css:153` `.dt-card > .dt-savebar { margin: 0 -16px -16px; padding: 12px 16px; }`

三处 padding/margin 叠在同一条底部边上。sticky 的 savebar 本身在流内占位，`padding-bottom: 48px` 又加一层。**未验证**：滚动到底时是否出现「一条 48px 的空白 + savebar 悬浮其上」的双层留白。需要浏览器里量 `scrollHeight - clientHeight`。

## D. 三端一致性

### D1 · P2 · 空态图标尺寸三处不一

| 位置 | 尺寸 | 圆角 |
|---|---|---|
| 桌面侧栏空态 | 52×52 | `RadiusFolderSml`（`ui.go:880`） |
| 桌面中栏空态 | 64×64 | `RadiusFolder`（`ui.go:1494`） |
| 手机 | 待查（`CrewUi.kt:362` `EmptyState`） | — |

`ui.go:879` 的注释已经主动说明了「圆角 20 那个是中栏的 64×64 空态，别混用」——说明这两个值是被有意区分的，不是笔误。但**为什么侧栏用 52、中栏用 64**，代码里没有理由。如果是设计稿定的，建议在注释里写明出处（现有注释已经引了 `画板 Desktop-empty.dc.html:31/51`，很好，保持一致）。

### D2 · P2 · 空态信息密度三端不同

桌面中栏空态（`ui.go:1495-1516`）有：64×64 图标 + 标题「还没有人说话」+ 副标题 + **三步引导**（`firstStep` × 3：说一句 / 接活后看进度 / 会记住对话）。

手机 `EmptyState`（`CrewUi.kt:362`）需要核对是否有对应的三步引导。如果没有，则首次使用者在手机上看到的是一个空屏幕 + 一句「队伍还是空的」，不知道该干什么。这是**新用户第一次打开**的路径，值得对齐。

### D3 · P2 · 「待命」vs「闲着」

- 桌面 `ui.go` 的 `stateOf` 在没有 task 时返回 `"待命"`
- `CrewWire.kt` / `CrewUi.kt:2141+` 的 `stateWord` 把 `"idle"` 映射成 `"闲着"`

同一个「没事干」的状态，桌面叫「待命」（书面、中性），手机叫「闲着」（口语、略带贬义）。BOT 是「同事」这个隐喻贯穿整个产品（「我的队伍」「今天由谁接手」），叫「闲着」和隐喻打架。

**建议**：统一成「待命」。若手机端要更短，用「空闲」。
