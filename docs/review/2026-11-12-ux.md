## 二、正面结论（值得保留）

### 正面 1：后端契约的「三值语义」设计是好的

`WorkStep.kind` 只有 `said / did / checked` 三个值，没有「第 N 步」「共 M 步」这类自造状态。这让客户端**不需要猜**进度——要么后端给了确定状态，要么就是没有。桌面原来错认成 `tool / error / say`，三种真实值全部命不中、一并落到默认最弱色，注释里承诺的「小圆点区分种类」实际没生效。**修的方向不是加状态，是回到契约的三值**。这个设计值得保留：状态枚举就该封闭、可穷举、有默认兜底。

### 正面 2：桌面端的「跨线程只经 `actionResult` / `deliver`」纪律

播报、录音、转码、播放这些全在后台 goroutine，主线程只改状态、不阻塞。`actions_test.go` 用 `deliver` 队列语义把它锁住。这是**对的**——GUI 线程一旦被网络或音频 IO 阻塞，用户看到的就是「点了没反应」。四个入口（`speak` / `voice` / `takeover` / 记忆编辑）全部遵守这条，没有一处例外。

### 正面 3（次要）：`record.go` 的 `voiceRecorder` 端口是可测试的

`voice_seam_test.go` 用 `fakeRecorder` 注入 `actionState.recorder`，整条链（录音 → 16k mono WAV → 真实 `POST /api/mobile/voice` → 文字只进草稿）都能自动化跑，真机验收只留给 GUI 与 TCC 弹窗。**端口划在这里是对的**——把「系统麦克风」这个不可测边界收在一个接口后面，其余全是纯逻辑。

## 三、反编造规则的遵守情况（逐条核对）

这套系统的反编造规则有三条，逐条对客户端核对：

### 规则 1：`unknown` → 不画进度条

**核对结果：遵守。**

- 桌面 `workDot` 对未知 kind 落默认色（`work_test.go` 有断言：未知 kind 落默认色，不冒充任何一种已知状态）。
- `CrewWire.kt:338` 解析 `total_steps` / `steps_done` 时，字段缺失走 `null`，`CrewUi.kt:2128-2147` 的进度条渲染以「两字段都非空」为前提 —— **没有数据就不画，不画 0%**。

**这是正面结论**：宁可界面少一块，也不给假进度。

### 规则 2：`empty` 与 `unavailable` 话术分开

**核对结果：遵守。**

- `empty` = 「确实没有内容」（列表为空，但系统正常）。
- `unavailable` = 「拿不到内容」（后端不可达 / 未实现 / 权限拒绝）。
- 桌面 `micStatusMessage`（`action_voice_test.go` 覆盖）在录音器不可用时报「这次编译没有 macOS 原生录音」，在录音收尾失败时报「录音没有正常收尾」——**两种话术不同**，没有合并成一句「出错了」。
- `TestVoiceStopRefusalShowsReason` 锁住：后端返回 `{available:false, reason:"没听出字来"}` 时，**原样显示 reason**，不吞成「识别失败」。

**这是正面结论**：错误文案分得开，用户能据此判断「是我没说话」还是「系统坏了」。

### 规则 3：没改动就没有「采用」按钮

**核对结果：遵守（且文档滞后）。**

- 契约 §5 写「手机端没接采用按钮」，但 `CrewUi.kt:2344-2468` 已实现，且显示条件绑定在「有可采用的改动」上。
- 桌面对应位置（`ui.go` 的票/结果区）同样只在有结果时出按钮。

**这是正面结论**：按钮不是常驻的，是**由数据存在性驱动**的。同时这条也是一处**文档债**：`docs/00-contract.md` §5 需要更新，否则下一个读契约的人会以为要补，实际已经在。

## 四、阻塞点与断头路

### 阻塞点 1：`docs/00-contract.md` §5 与实现不一致（P0）

契约说手机端没接 `total_steps` / `steps_done`、没接「采用」按钮，但：

- `CrewWire.kt:338` —— 已解析
- `CrewUi.kt:2128-2147` —— 进度条已渲染
- `CrewUi.kt:2344-2468` —— 采用按钮已实现

**后果**：读契约的人会去「补」已经存在的东西，或者误判客户端能力缺口。这不是代码 bug，是**协作文档失真**，但危害等同——它会让下一轮工作方向错误。

### 断头路 1：桌面端四个入口只有 `go test` 级证据（P1）

`speak` / `voice` / `takeover` / 记忆编辑四条链路，全部没有真机验收：没启动过窗口、没真录音、没真出声。`TestAgainstTheLiveGateway` 按设计 `t.Skip`（需要真后端在跑），这是「未做联调」的机器可读证据。

**用户会卡在哪**：打包成 `.app` 后首次按「录音」会弹 TCC 麦克风授权。`NSMicrophoneUsageDescription` 已加（`desktop/Info.plist:23`），但**没在真机上验证过弹窗文案和拒绝后的降级路径**。如果用户点了「不允许」，`micStatusMessage` 应该报「麦克风权限被拒绝：到「系统设置 → 隐私与安全性 → 麦克风」允许这个桌面 App」——这句话在测试里断言过，但没在真系统上见过。

### 断头路 2：Android 侧本轮几乎全未验证（P1）

配对、派活、发送中状态、记忆列表 —— 这些在 Android 客户端的具体行号与行为，本轮**没有足够静态证据**。唯一的确定性来自 `CrewWire.kt` / `CrewUi.kt` 的三处已定位实现（进度条、采用按钮、步骤解析）。

**不能说「Android 好了」**，只能说「这三处有代码」。

### 断头路 3：平台边界是硬边界（P2）

- 录音只有 **darwin + cgo** 有实现（`record_darwin.m`）；其它平台 `record_stub.go` 明确报「这次编译没有 macOS 原生录音」。
- 播报走 `afplay`，Linux / Windows 上会在 `exec.LookPath` 处如实说没有系统播放器。

**这是对的**——不假装有麦克风、不假装能出声。但意味着**跨平台用户会撞墙**，且墙是硬的（不是降级，是明确不可用）。
