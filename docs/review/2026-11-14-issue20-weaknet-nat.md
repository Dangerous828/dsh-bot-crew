## 一句话结论

- **第 2 项（`probeBudget()` 真实超时）能验，已验完，并且验出一个真缺陷**：预算对「对端完全静默」
  有效（实测封在 20.17s），对「对端慢滴」**失效** —— 实测 21.07s / 41.23s / 81.64s，**无上界**。
- **第 1 项（跨 NAT 打洞成功率）在本机拿不到条件**。真实跨主机隧道跑了 120/120，但
  `tailcat ping --until-direct` 显示升级后走的是 `192.168.31.175` —— **同一 NAT 内的 LAN 直连，
  不是跨 NAT 打洞**。按 issue 的收口线，这组数字**不能**用来收口第 1 项。
- 因此 #20 仍**外部阻塞**，缺的东西写在文末「缺什么」一节，逐项到具体 peer / 网络 / 窗口。

## 一、第 2 项：`probeBudget()` 在真实超时下的行为

### 设计意图（读代码确认）

`app/.../TailcatP2p.kt:169` 的 `probe()` 给整轮 20 秒预算（`PROBE_BUDGET_MS`），
每步开始前用 `probeBudget(deadline, now, waitMs)` 算出「这一步还能等多久」，把结果当
`HttpURLConnection.readTimeout` 传下去；耗尽返回 `-1`，调用点据此放弃这一步。

设计意图是：**整轮探测不超过 20 秒**，别把调用线程占满（`d0a0668` 的提交信息写明动机：
Wi-Fi 断连时三步各等满 15 秒 = 45 秒，主线程上的调试口与界面跟着排队，真机全黑屏）。

### 实测：预算在「对端静默」时有效

台架 `probe_server.py` 的 `hang` 模式收下请求、永不回应，等价于「隧道那头不回」。
直接调用产品 `probe()`（`ProbeHarness.kt`，不改一行探测逻辑）：

| 用例 | 单步上限 `waitMs` | ok | 墙钟 | 判定 |
|---|---|---|---|---|
| C 对端收下不回 | 15 000ms | false | **15.12s** | 单步超时先触发，预算未成约束 |
| D 对端收下不回 | 60 000ms | false | **20.17s** | **预算生效**，把 60 秒的单步封在 20 秒 |

D 是这一项的核心证据：把单步上限放到 60 秒，实际 20.17 秒就返回了 —— 预算确实拦住了。
C 说明在默认 15 秒单步下，先到的是单步超时而不是预算，这是设计预期，不是缺陷。

### 实测：预算在「对端慢滴」时失效（新发现的缺陷）

`readTimeout` 是**每一次 `read` 的期限**，不是整步的期限。对端只要在期限内持续吐字节，
就没有任何一次 `read` 会超时 —— 于是整步墙钟由「字节数 × 每字节间隔」决定，与 20 秒预算无关。

`probe_server.py` 的 `drip` 模式一个字节一个字节地发，每字节间隔可调。响应约 100 字节：

| 每字节间隔 | 墙钟 | 是否越过 20s 预算 |
|---|---|---|
| 100ms | 22.52s | 是（且 `ok=true`，被当成一次「成功但很慢」的探测） |
| 200ms | **21.07s** | 是 |
| 300ms | **31.15s** | 是 |
| 400ms | **41.23s** | 是 |
| 800ms | **81.64s** | 是（上限放到 240s 才跑完） |

800ms 那例的墙钟 81.64 秒 = 约 100 字节 × 0.8 秒，与「每字节间隔 × 字节数」吻合，
证明**限制来自对端节奏而不是本端预算**。把间隔再放大，墙钟就再线性放大 —— 没有上界。

对照 `run_probe_matrix.py` 的 H 例（同样 800ms/字节，但外部上限只有 75 秒）：进程在
75.01 秒被外部杀掉，`probe()` 自己还没返回。这就是「预算没封住」的最直接形态。

### 这个缺陷的实际影响

- 预算存在的**唯一理由**是「别把调用线程占满」。慢滴对端让这个理由失效：线程仍可能被占住
  数十秒到无限（取决于对端）。
- 它比 `d0a0668` 修掉的那个坑（`readTimeout=0` = 无限等待）**弱一档但不是无害**：
  `readTimeout=0` 是永久挂住，慢滴是「长度由攻击者/劣化链路决定」。弱网、限速、
  丢包重传、被中间设备做流量整形的链路，恰好就是慢滴的典型形态。
- 注意 `ok=true` 那两例（100ms/200ms）：一次「实际花了 20 多秒」的探测会被记成成功，
  `millis` 也会被写成 11 715ms 这种值。界面上「隧道通了但很慢」与「隧道没通」是两种状态，
  这里会把前者报成后者之外的东西 —— 说得更准些：**它报成了「通」，而真实情况是「慢到不可用」**。

### 修的方向（本轮只记录，不改代码）

预算要变成**整轮的墙钟上限**，而不是「每次 read 的期限」。可选做法（按代价从低到高）：

1. 探测跑在独立线程/协程里，主流程用 `Future.get(20s)` 或 `withTimeout(20s)` 收口 —— 改动最小，
   且不依赖 `HttpURLConnection` 的语义。
2. 自己读正文：不调 `readBytes()`，改成循环 `read()` 并累计已用时间，超预算就 `disconnect()`。
3. 两条都做：预算管收口，`disconnect()` 管真正中断在途 IO。

单测可以钉住第 1 条：给 `probe()` 一个「永远慢滴」的本地 socket，断言墙钟 < 预算 + 容差。
这正是本轮台架已经在做的事，可以直接搬进 `app/app/src/test/`（本轮按红线不改产品测试目录）。

## 二、第 1 项：跨 NAT 打洞成功率

### 能验到的部分：真实跨主机隧道

拓扑（全部为真实进程，无模拟）：

```
Mac (手机侧)                          win-desktop (电脑侧)
tailcat forward 127.0.0.1:43511  →隧道→  tailcat serve 43510  →  python 可控服务器 :43510
      ↑
产品 probe() 打 43511
```

用独立 key（`i20probe` / `peer`）、独立端口（43510/43511），**不碰生产那条 43499 隧道**。

| 测量 | 结果 |
|---|---|
| 产品 `probe()` 连续 120 轮 | **120/120 成功，0 失败**；稳态 5–7ms（`soak-120.txt`） |
| 失败路径：拿掉隧道那头的服务 | 5/5 轮在 **10–37ms** 内快速返回 `ok=false`，**没有挂死** |
| 恢复后 | 5/5 轮 `ok=true`，5–6ms，**自愈**（`failpath.json`） |
| 产品退避序列（`CrewRoute.retryDelay`） | 1s / 2s / 4s / 8s / 16s / 30s / 30s…（实测调用得出，与注释一致） |

失败时的行为**如实**：快速失败、不挂死、恢复后自动回通、退避有界。这一半是可信的。

### 为什么这组数字**不能**用来收口第 1 项

`tailcat ping --until-direct` 的输出直接给出了升级后的对端地址：

```
pong in 144.77ms via DERP(tok)
pong in 2.78ms via 192.168.31.175:59751     ← 升级到了 win-desktop 的局域网 IP
```

30 次**新连接**的路径分布（`path-30.txt`）：

| 路径 | 次数 | 说明 |
|---|---|---|
| `DERP(tok)` 中继 | 19 | 188ms 量级 |
| `192.168.31.175`（win-desktop LAN IPv4） | 4 | 4–5ms |
| `2409:8a55:2236:2590:303a:cef0:2496:ee1b`（win-desktop 全局 IPv6） | 7 | 4–5ms |

两台的全局 IPv6 在**同一个 /64**：

```
Mac:         2409:8a55:2236:2590:1840:259c:ef38:3d90
win-desktop: 2409:8a55:2236:2590:f94c:d521:891d:95db
             ^^^^^^^^^^^^^^^^^^^^^^^^ 同前缀
```

IPv4 也同网段（`192.168.31.127` / `192.168.31.175`，小米 `192.168.31.0/24`）。
**两台机器在同一个 NAT 后面，共享同一个公网出口。** 所以那些 4–5ms 的「直连」是
**同 LAN / 同 NAT 内的直连**，`192.168.31.175` 这个地址本身就是证据 —— 它不是公网地址。

这正是 issue 正文警告的那件事：「这组数字证明的是『当前网络测不出来』，不是『已修好』」。
本轮把这句话从判断变成了**可复现的证据**：不是「看起来像同网」，是 `tailcat` 自己把
对端报成了 `192.168.31.175`。

### 唯一拿到的「中继」数字

19/30 新连接落在 DERP(tok) 上，单程 144–203ms。这是**中继**的数字，不是打洞的数字 ——
DERP 是打洞失败时的兜底，走它说明「没打通但通了」。

对产品行为的意义：`probe()` 的 `ok` 只看「隧道能不能承载真请求」，不看走的是直连还是中继。
代码注释已经写明这个取舍（「打洞没成功时 tailcat 会退到 DERP 中继，请求照常通，
但一个来回是 137ms 而不是 1.4ms —— 界面按 millis 说实话，不拿『通』冒充『直连』」）。
本轮实测印证了这段注释：中继 144–203ms、直连 4–5ms，量级差 30–40 倍，`millis` 确实能区分。

但**区分得了「直连 vs 中继」不等于「测出了打洞成功率」**：同一 NAT 内本来就不需要打洞。

## 三、缺什么（具体到 peer / 网络 / 窗口，不是「需人工」）

要真正收口第 1 项，需要**一个与 Mac 不同 NAT 出口的对端**。逐个候选核过：

| 候选 | 现状 | 差什么 |
|---|---|---|
| **win-laptop**（`192.168.0.109` / EasyTier `10.10.10.1` / 公网 IPv6 `win.kentonnie.top`） | **三条路全不可达**：`192.168.0.109:22` 超时、`10.10.10.1:22` 超时、`win.kentonnie.top:22` 超时 | 这台在 TP-Link `192.168.0.0/24`，是**唯一现成的第二个 NAT 出口**。需要它开机并接入网络（或用户在 TP-Link 网内），然后给它放一份 Windows 版 tailcat 客户端 |
| mi-desktop（`192.168.31.183`） | `:22` 超时 | 与 Mac 同网段同 NAT，**即使通了也不满足跨 NAT** |
| NAS（`192.168.31.152`） | `:22` 拒绝 | 同 NAT；且 Linux 版需要重新编（本机 Windows 交叉编译链只解了 Windows） |
| 公网 VPS / 云主机 | 本仓库无任何此类节点配置 | 没有可用凭据与地址 |

所以**唯一现实的路径是 win-laptop**。需要的具体条件：

1. **win-laptop 开机并联网**（现在三条路都不通，无法判断是关机、休眠还是网络变更）。
2. 一个**独立网络窗口**：它必须在 TP-Link `192.168.0.0/24` 那个出口上，不能搬到小米网段 ——
   一搬就和 Mac 同 NAT，条件立刻消失。这一点需要 owner 确认，因为它涉及物理位置/网络归属。
3. 在它上面跑客户端：`i20-tailcat.exe`（本轮已编出，19MB，`0bedfee19a98147f8408` 开头）。
   若它也在代理后面（win-desktop 就有个失效的 `127.0.0.1:7897`），要清 `HTTP_PROXY` 等环境变量。

拿到这三样，本文的 `failpath.py` 与 `ProbeHarnessKt` 可以原样复用，只需把目标从
`43511`（Mac 本地 forward）换成「本机 forward 到 win-laptop serve」的端口。
**台架不用重写。**

### 另一种可能：不靠第二台机器

如果 owner 能提供**一个不同出口的网络**（手机热点、另一条宽带、公司网），也可以：
让 win-desktop 连那条网络（改它的 Wi-Fi 会动到生产环境，需要 owner 同意），
Mac 留在小米网段。这样两台就在不同 NAT 后。代价是打断 win-desktop 上的 H3/ComfyUI 生产。

## 四、边界声明（哪些不算数）

- **代理层弱网 ≠ UDP 打洞 NAT 条件**。`probe_server.py` 的 hang/drip/delay 只作用于
  **已经建立的 TCP 连接**，不涉及 NAT 类型、端口预测、UDP 打洞、DERP 注册。第 2 项的结论
  只用在这一层，不外推到打洞。
- **LAN 20/20 不等价弱网跨 NAT**。本轮 120/120 是同 NAT 直连，已在上文标注，不当收口证据。
- **未做**：未改系统网络/路由/防火墙/VPN/Wi-Fi/限速；未碰手机（`ds-pairing-ui-max` 正在用）；
  未读凭据内容（只读了 mobilegw 自己生成的临时 token 长度，未打印值）；
  未重启 dsh / mobilegw；未 git 任何操作。
- **台架自污染一次已修正**：第一版 `probe_server.py` 用 keep-alive，而 `probe()` 用
  `readBytes()` 读到 EOF 才返回，凭空造出 5 秒延迟，把 A/B 两例污染成假超时。
  改成 `Connection: close` 后重跑，数据才干净。这条写进 `docs/review/i20/README.md` 防止复发。
