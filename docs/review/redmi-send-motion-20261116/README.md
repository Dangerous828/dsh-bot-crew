# 红米发送过程动态验收

设备：Redmi 24117RK2CC，ADB `9f9cc3db`，1440×3200。保留原配对、历史与未提交修改；本轮不 commit/push。

## 可重复反馈环

录制：`python3 docs/review/redmi-send-motion-20261116/capture_motion.py <capture-directory>`。

验证：`python3 docs/review/redmi-send-motion-20261116/verify_motion.py <capture-directory>`。

UI 快照验证只检查可观测状态；仍须用 look_video 检视录屏，尤其发送、回复到达、缓存刷新和收起键盘附近的连续帧。录屏本身无音轨，属于视觉排障证据。

## 已观察到的复现

`repro-send.mp4` 连续录制 35 秒，`repro-events.json` 记录同一单调时钟上的操作时刻。

- 3.336 秒点击发送；键盘继续保持打开。
- 约 6–7 秒出现新用户消息和不相关的「子代理／点开看」卡。
- 9.285 秒点击卡，随后出现「读着…」与「· 读着…」两行。
- 新回复到达后，卡片展开状态消失并回到「点开看」。
- 原生 VFR 帧在 17.100 秒与下一帧 17.619 秒之间显示卡片从存在变为消失，消息整体下移；键盘位置保持不变。视频未提供该间隔内的独立帧，不据联系图请求时间宣称更细的先后或因果。操作脚本时钟与编码视频起点也未精确校准。
- IME 打开期间，顶栏菜单 bounds 均为 `[0,0][0,0]`，完全离开可见窗口；收起 IME 后恢复 `[85,220][142,312]`。
- 同一阶段 Composer 一直是 `[259,1741][1079,1951]`，没有证据支持将这次跳动归因于短文本输入框自身变高。

真实发送为 message 75「hi」，reply 61，决定 `answeredDirectly`；工单总数保持 28，因此本次没有派工，子代理卡不是这次请求产生的工作。数据见 `real-send-state.json`。

首次运行上述验证命令已得到退出码 1，具体命中顶栏出视口、不相关子代理卡、双 loading。报告为 `motion-verification.json`。

## 当前代码收口范围

由原 Luna max Android 成员独占实施全部 Android 源码及测试：

- 使用统一的原生 IME/insets 处理，保持顶栏和输入区边界稳定。
- 刷新时保留已有的产出/代理树数据，未读与空结果不生成可点的临时卡壳；不让普通聊天反复重置历史票加载状态。
- 不因滚动直接卸载已显示结果条并改变消息高度。
- 跟随依据真实列表尾部及用户阅读意图，不让异步卡片变动改变视口落点。

完成条件：相应失败回归变绿，JDK21 同签构建覆盖红米；在同一手机重录发送过程，验证脚本通过，且 look_video 连续帧检查通过。仅终态截图或纯 helper 单测不构成本轮验收。

已知独立事项：后台睡眠唤醒后的 mDNS 异常退出仍见上一轮运行事件，本轮 UI 收口不宣称修复该后台问题。
