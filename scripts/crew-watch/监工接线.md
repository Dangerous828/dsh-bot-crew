# 用 dsh-bot 给 crew 做监工 · 接线单

## 先看现场（2026-11-11 实测）

crew 后端跑在 `127.0.0.1:3082`（独立 superagent profile），管理接口 `GET /orchestrator/api/state` 返回 200。当前快照：

```
paused=False  load={running:0, queued:0, maxWorkers:3}  tickets.total=0
health: runtime/relay/notice/launch/delivery/assessment/reply/models/github/team = ready
        evals = error
accounts: repository=Dangerous828/dsh-bot-crew, agent=Dangerous828
```

`evals=error` 的含义是「过去一小时有 Eval 不可用且未被判定/忽略」，正是会出现「消息进来了但永不开工单」的那种状态。**它现在没人报告**——这就是监工要补的第一件事。

## 一、能补什么，补不了什么

| 层次 | dsh-bot 做监工 | 依据 |
| --- | --- | --- |
| 看得见：定时读 health / load / tickets / decisions，异常告警、出报告、留运行记录 | ✅ | `@zifeng1023/dsh-bot` 0.3.6 有 `http_get`（可 `allowPrivate` + 自定义 headers + `pick`）、`bot_schedule`（cron）、`bot_runs`、通知 |
| 判得准：用模型比对「谁接了活 / 谁越界干了别人的活 / 哪张工单卡太久」 | ✅ 事后发现 | ticket 带 `bot_id`、回话带署名，decisions 有研判记录 |
| 停得下：`POST executor/pause`、`POST tickets/<id>/stop` | ❌ | `http_get` 是 **只读 GET**（副作用等级 `none`），25 个工具里没有写操作；急停要走下面的外挂 |
| 管得住 worker 的角色边界、OS 隔离、多会话视图 | ❌ | 属于 crew 内核，见第三节 |

结论：**装 dsh-bot 当监工 = 把「没人看」变成「有人定时体检 + 判定 + 告警 + 留痕」；它不会改 crew 的一本账，也管不住 worker。**

## 二、主路线：`@zifeng1023/dsh-bot` 0.3.6（不改 crew 一行代码）

### 1. 数据面（已实测可用）

crew 的管理围栏只认 loopback Host + `x-orchestrator-request: 1`，`http_get` 两个都能给：

```json
{
  "url": "http://127.0.0.1:3082/orchestrator/api/state",
  "headers": { "x-orchestrator-request": "1" },
  "allowPrivate": true,
  "pick": "health|load|paused"
}
```

同法读 `/tickets`（`total|items`）、`/decisions`（`items`）、`/settings`（`blocks.eval.value.model|blocks.executor.value.model`）、`/sources`。`pick` 把大响应压成几行，别把 20k 截断喂给模型。

### 2. 监工 Bot 的一句话目标（可直接 `bot_adopt`）

> 每 5 分钟读一次本机 crew 的 state / tickets / decisions / settings：任一部件不是 ready 或 paused、evals 为 error、有工单但 running=0、queued 超过 maxWorkers 两倍、eval/executor 模型未钉死、Source 掉线，就写一条中文告警并推送；全绿时只记一行「正常」，不打扰。所有动作先 dry-run，不许改 crew 的任何设置。

### 3. 判定规则表（也写进了 `crew-watch.py`）

| 信号 | 判据 | 动作 |
| --- | --- | --- |
| 部件异常 | `health.*.state ∉ {ready, paused}` | 告警，附 detail |
| Eval 卡住 | `health.evals.state == error` | 高优先级告警 |
| 工单没人干 | `tickets.total > 0 && load.running == 0 && !paused` | 告警 |
| 积压 | `load.queued > maxWorkers × 2` | 告警 |
| 模型未钉死 | `blocks.{eval,executor}.value.model == null` | 提醒（不算故障） |
| Source 掉线 | `GET sources` 里 state 不在 ready/off/paused/missing（`mobile` 默认 disabled 报 missing，属预期） | 告警 |

### 4. 急停外挂（补 `http_get` 只读的缺口）

监工只报告，停机交给一条独立命令（人工或 launchd 定时兜底）：

```sh
# 全局暂停派工
curl -s -X POST -H 'Host: 127.0.0.1:3082' -H 'x-orchestrator-request: 1' \
  -H 'content-type: application/json' -d '{"paused":true}' \
  http://127.0.0.1:3082/orchestrator/api/executor/pause
# 停单张工单
curl -s -X POST -H 'Host: 127.0.0.1:3082' -H 'x-orchestrator-request: 1' \
  http://127.0.0.1:3082/orchestrator/api/tickets/<id>/stop
```

### 5. 安装（会重启 DSH，故留到确认后执行；用独立 profile 不碰现在这个会话）

```sh
PROFILE=crew-watch
dsh "$PROFILE" --from-default-profile web --dump-config >/dev/null
dsh plugin --profile "$PROFILE" add @zifeng1023/dsh-bot@0.3.6
dsh web --profile "$PROFILE"      # 重启后在该 profile 里 bot_adopt 上面那句话
```

宿主兼容：`engines.dsh >=0.2.0-0 <0.3.0-0`；官方 README 说在 `0.2.1-rc.x` / `0.2.2-rc.x` 验证过，升级宿主后先看 `bot_doctor`。

## 三、你对 crew 不满意的三条，监工治不了

[source: Super Agent 自动工作参考; baseId=f02adfb3-be60-4232-a1bd-ccbf46684eae; docId=0aad7607-13bc-494d-a4f6-9eacd6bafdb0; chunkId=7c5fe4bc-ea94-4f8b-ab2f-48790df70f3f; title=本机 dsh-bot-crew README（前台 Bot 队伍与两层架构）; heading=dsh-bot-crew > 状态]

- **worker 都有完整能力，提示词劝不住它替队友干活** → 监工只能靠 `bot_id` 署名与工单归属做事后检测；事前约束要在 crew 后端加工具级硬门禁。
- **隔离是约定不是强制**：所有 worker 跑在同一 OS 用户下，别的 Bot 的记忆文件读得到 → dsh-bot 也跑在同一 OS 用户下，补不了；要独立账号 / 容器。
- **前台还是「一个对话 + 一排 Bot」，没有多会话/群组视图** → 这是前台问题，监工不改 UI。

## 四、兜底与草稿路线

- **兜底（不装任何插件）**：`python3 crew-watch.py --port 3082` 直接输出告警 + JSON，退出码 0/1/2；挂 launchd 每 5 分钟跑，异常时发通知。零第二本账、零重启。
- **草稿（真要换主管层）**：`ds-bot` 0.3.2 的 Chief + Goal 才是「分阶段派活、逐阶段验收」的监工语义，`dsh-bot-board` 0.7.3 是配套看板（谁在跑/谁卡住/谁需要你）。但两者都只读 DS Bot 自己的 `~/.dsh/bot/state.json` 与 `api/bot`，**看不到 crew 的 Ticket**；要把 crew 接进去等于换主框架，先在独立 profile 实测再决定。
